# Preparación de OAuth de Intervals.icu

Revisado el 2026-11-11. Diseño futuro; este lote no registra aplicaciones ni implementa OAuth.

1. **Registro.** Seguir la [guía oficial del foro](https://forum.intervals.icu/t/intervals-icu-oauth-support/2759). Ahora el alta se solicita en `https://intervals.icu/oauth/apply` con la cuenta propietaria; esperar aprobación. Preparar nombre, web, logo, privacidad y redirects de desarrollo/producción. La gestión posterior aparece en Settings → Apps → Manage App. El registro por correo mencionado en versiones antiguas de la guía ya no es el primer paso.
2. **Consentimiento y callback.** Solicitar solo `ACTIVITY:READ`, con `state` aleatorio ligado a la sesión de Supabase, de un uso y con caducidad. Usar PKCE S256. Registrar un callback HTTPS concreto que reciba los parámetros antes del hash de la SPA; tratar denegación y verificar `state`. No poner códigos ni tokens en logs o analítica; limpiar la URL al terminar.
3. **Edge Function de Supabase.** Propuesta para FBikeTrain: validar JWT del usuario y la transacción iniciada, intercambiar el code en `POST https://intervals.icu/api/oauth/token` dentro de dos minutos e incluir `code_verifier`. Si el registro es confidencial, `client_secret` solo en secretos del servidor; el proveedor también permite clientes públicos con PKCE obligatorio. No incluir secretos en Vite.
4. **Tokens.** Diseñar una tabla privada por `auth.uid()`, sin lectura pública, con acceso de servidor y cifrado gestionado en servidor; definir revocación/desconexión y borrado. Guardar atleta real y scopes concedidos para mapear la cuenta. La documentación actual describe access tokens, sin refresh tokens: confirmar vigencia y respuesta real al registrar, sin inventar un flujo de renovación. No migrar automáticamente las API keys personales al servidor. `resolveIntervalsConnection` adaptará esa sesión al proveedor `authorization(signal)`; `intervalsSync` conserva su lógica.
5. **Webhooks, opcional.** Existen y se activan en Manage App. La [guía oficial de integración](https://forum.intervals.icu/t/intervals-icu-api-integration-cookbook/80090) documenta POST con secreto y eventos `ACTIVITY_UPLOADED`/`ACTIVITY_ANALYZED`; no entrega actividades procedentes de Strava. Otra Edge Function validaría el secreto y la asociación atleta/cuenta, acotaría el cuerpo y deduplicaría eventos. El evento dispararía una reconciliación autenticada, no importaría el payload como track. Responder 2xx tras encolar de forma fiable y prever reintentos/desorden. Procesar con la app cerrada requeriría además una cola y ejecución de importación de archivos en servidor: no lo resuelve un webhook por sí solo.

Antes de uso multiusuario: probar consentimiento, callback denegado/manipulado, token revocado, aislamiento entre dos cuentas, borrado y repetición de webhooks. Revisar cuotas OAuth en la [guía de acceso](https://forum.intervals.icu/t/api-access-to-intervals-icu/609). No hay backend nuevo ni migración SQL en la revisión actual.
